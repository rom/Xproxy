# Examples

Ready to adapt configuration fragments and rule files. Every file here
is validated by `go test ./test/examples/`: the YAML documents pass the
configuration parser and each one's listeners are checked against the
daemon that serves them, the
configuration parser, the SecLang files compile with the Core Rule Set
and block what they say, the block list loads, the WebAssembly module
runs through the filter, and the rewriting rules apply to sample bodies.
Paths inside the files follow the Fedora layout (`/etc/xproxy`); on
macOS replace the prefix with `/usr/local/etc/xproxy`.

The `Daemon` column says which of the three serves a file's listeners:
`xproxy` (the edge), `xgate` (the bastion) or `xrelay` (the
machine-to-machine relays). A fragment with no listeners — a rule file,
a block list, an include of routes or filters — belongs to whichever
daemon names it.

| `databases/` | `postgres.yaml`, `mysql.yaml`, `tds.yaml`, `redis.yaml` | xrelay | A PostgreSQL relay, which is deliberately **not** a SQL firewall: knowing which tables a statement touches means parsing SQL properly, and a relay that got that 95% right would have a hole in exactly the place somebody is looking -- so restricting a role's tables stays the database's job, with GRANT. What is here instead is the four things a relay can do. It refuses the encryption downgrade, which is the whole reason to put one in front of this protocol: TLS is negotiated in cleartext, eight octets ask and one unsigned octet answers, and libpq's default sslmode is `prefer` -- "carry on in the clear if refused, without telling anybody" -- so one line here fixes for every client at once what ten thousand connection strings will not. It refuses the authentication methods whose credential an observer can reuse, `md5` among them, whose stored verifier is a password-equivalent. It refuses what is not a statement at all: a replication connection, which is a startup *parameter* and a byte-for-byte copy of the whole server, the legacy fast-path function call, and a cancel request the server would act on with no authentication whatsoever. And it decides by the *shape* of a statement, as an allow list of kinds where anything the classifier cannot name is refused -- which stops `COPY ... FROM PROGRAM` (remote code execution with a SQL keyword in front of it, and nameable by no rule in any mode), a data-modifying CTE wearing a SELECT's leading keyword, and the `; DROP TABLE` half of an injection. Three listeners: a reporting front narrowed until it says one checkable sentence, an application front where a *rule* lets the migration account change the schema on two nights a week and nothing else ever, and a shadow-mode trial that still refuses the hard shapes, because relaying remote code execution and writing it down is not a trial of anything . And MySQL, where the dangerous things are *commands* rather than statements: COM_SHUTDOWN is one octet and stops the server, three more open a stream of every change to every database, and COM_CREATE_DB and COM_DROP_DB predate the DDL statements entirely -- none of which a relay that only classified SQL would ever see. Two are subtler and are why a capability policy alone is not enough: COM_CHANGE_USER re-authenticates a *live* connection as somebody else, and COM_SET_OPTION turns multi-statements on *after* the handshake is over. The move this kind makes that no other does is to rewrite the server's greeting -- MySQL's handshake runs the opposite way round, the server speaking first, so the relay clears the capability bits the policy denies and forwards the edited one. A client that never sees CLIENT_LOCAL_FILES offered cannot negotiate it, so the server can never ask that client for a file, **and the application still works**: rewrite rather than refuse, the same choice the tftp kind makes with its window. Three listeners: an application front, a replication front where a rule lets exactly one account from exactly one address stream the binary log, and a trial. And SQL Server, where three things are different again. The password in a LOGIN7 is XOR 0xa5 with the nibbles swapped -- an encoding, with no key -- so `require_tls` here is not hardening but the difference between a reusable credential on the wire and none; and the negotiation that decides it is one unsigned octet in a PRELOGIN option table, where `off` means "I would rather not" and `not_supported` is what an attacker rewrites the server's answer to, so the relay answers ENCRYPT_REQ itself and logs every connection whose negotiation it raised, which is the list to read *before* turning the setting on. The dangerous operations are procedures rather than statements or commands -- `xp_cmdshell` is a shell command as the service account, the `sp_OA` family is arbitrary COM, `sp_addlinkedserver` turns one compromised database into a route to another, `sp_configure` is how the first of those gets switched back on -- and to a statement classifier every one of them is an EXECUTE, so procedures get their own allow list defaulting to what a driver calls, with that set refused even in monitor mode. And the statement an application runs is not a statement: every client library that uses parameters sends `sp_executesql` with the SQL as a parameter, so the relay reads that one parameter -- and only that one, the rest being the caller's data -- and applies the same statement policy to it as to a batch. The odd structural detail is the TLS handshake, which is carried inside TDS packets until it completes and outside them afterwards: the nesting inverts once, part way through a connection. Three listeners: an application front, a reporting front where a schedule confines the nightly extract to its window, and a trial. And Redis, which is the protocol where a relay earns its place fastest, because Redis's own default is no password: an instance that is *reachable* is one that is *administrable*, and the distance from an administrative command to a shell is three of them -- `CONFIG SET dir`, `CONFIG SET dbfilename`, `SAVE`, which writes a file of the attacker's choosing wherever the server can write. There is also almost nothing to reason about: a command is an array of opaque byte strings, with no schema and no statement grammar. So the policy is authentication first -- refusing any command before the connection has authenticated, with the answer taken from the *server's* reply rather than from having seen an AUTH, because a relay that trusted the attempt would treat a wrong password as a login -- then a command allow list whose absences are the value (`MODULE LOAD`, the Lua interpreter, `REPLICAOF`, `MIGRATE`, `FLUSHALL`, `MONITOR` which streams every value any client writes, and `KEYS`, which is O(n) on the single thread serving every client so one of them is an outage that reads as a slow query), then the subcommand where it decides `CONFIG GET` from `CONFIG SET`, then a key prefix policy -- which is the closest this protocol has to the boundary the SQL kinds leave to GRANT, and which refuses the ten commands whose key positions depend on an option rather than checking the wrong argument and passing what it was meant to stop. Three listeners: an application front, an operations front where a Sunday-night window is the only time FLUSHDB exists, and a trial |

Use a file with `xproxy -config FILE -validate` (or `xgate`/`xrelay`;
each validates the whole file whichever listeners it holds), or copy the
section you
need into the daemon's own file in `/etc/xproxy/` (fragments with only `routes`,
`upstreams`, `rate_limits` or `filters` can go to `/etc/xproxy/conf.d/`
with `includes: [/etc/xproxy/conf.d/*.yaml]` in the main file). The
reference for every key is [docs/CONFIG.md](../docs/CONFIG.md); the
operating patterns behind the examples are in
[docs/USAGE.md](../docs/USAGE.md).
