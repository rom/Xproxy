# IEC 60870-5-104 — telecontrol for the grid

`kind: iec104`, served by **xot**, TCP port **2404** (and **19998** for the
IEC 62351-3 TLS variant).

The protocol a control centre speaks to a substation gateway. IEC 60870-5-101
defined the application layer for a serial link; **-104** puts it on TCP,
keeping the type identifications and causes of transmission unchanged, which is
why the two standards have to be read together.

## On the wire

Two layers.

**APCI** — the application protocol control information — is six octets: a
start octet `0x68`, a length, and four control-field octets that decide which
of three formats this is.

| Format | What it is | What it carries |
|--------|-----------|-----------------|
| **I** | Information transfer | A send sequence number, a receive sequence number and an ASDU |
| **S** | Supervisory | A receive sequence number alone: an acknowledgement |
| **U** | Unnumbered control | One of `STARTDT`, `STOPDT` or `TESTFR`, each as an activation or a confirmation |

**ASDU** — the application service data unit — is where the meaning is:

- A **type identification**: `M_SP_NA_1` (single-point information),
  `C_SC_NA_1` (single command), `C_RC_NA_1` (regulating step command),
  `C_SE_NA_1` (set-point command), `C_IC_NA_1` (interrogation), `C_CS_NA_1`
  (clock synchronisation), `C_RP_NA_1` (process reset) and about forty more.
- A **cause of transmission**, which is how the same type identification means
  "here is a value", "please do this", "I have done it" or "I refused".
- A **common address** (ASDU address), naming the station.
- An **originator address**, naming which control centre asked.
- One or more **information object addresses**, each naming a point.

The `k` and `w` windows bound how many I-format frames may be outstanding
before an acknowledgement, which is the protocol's own flow control.

**And a connection is usually not alone.** Edition 2 of the standard describes
**redundancy groups**: a control centre opens several connections to a
substation over different routers or bearers, exactly one of them carries data
at a time, and the controlling station moves data transfer with `STARTDT` when
a path fails. The standby connections stay open and exchange `TESTFR` and
nothing else.

## What the protocol gives you

In the base standard, nothing. No authentication, no integrity, no
confidentiality. The originator address is a number a sender writes, not a
credential.

**IEC 62351-3** adds TLS, and it is real transport security with mutual
authentication where both ends support it. It starts at the first octet on its
own port rather than being negotiated inside the protocol, which is the right
choice — there is no downgrade to trip over.

The standard also *describes* **select-before-operate**: a command may be sent
as a selection first and an execution second, so a control room's operator
confirms before anything moves. It describes it, and much of the equipment in
the field will accept a direct execute without ever having been selected.

## What this listener decides

The policy is written in the standard's own vocabulary, which is what makes it
reviewable by the people who wrote the substation's point list:

- **The type identification**, so the commands a control centre may send are
  named one at a time. `allow_controls` is the list; the monitoring directions
  are separate, because reading the grid's state is not the same permission as
  changing it.
- **The cause of transmission**, because a type identification with the wrong
  cause is a command dressed as a report.
- **The common and originator addresses**, so a listener in front of one
  substation cannot be used to reach another, and a command can be attributed
  to the control centre that sent it.
- **The information object address ranges**, which is where "these breakers and
  not those" is written.
- **Select-before-operate, enforced.** `require_select` makes the relay hold
  the standard's own sequence: a direct execute with no selection in force is
  refused, the selection expires after `select_timeout`, and
  `max_selections` bounds how many may be open. The standard describes this and
  the equipment mostly does not, so the relay is where it becomes true.
- **Which connection of a redundancy group may carry data.** `redundancy.groups`
  declares which connections are one controlling station; only the one holding
  data transfer may send anything, and taking it from a live path is a logged
  failover. See below.
- **The value a setpoint carries**, which is the one thing a rule about type
  identifications cannot say. `setpoints` bounds a point's value (`min`, `max`)
  and how far one command may move it (`max_delta`), so "the pressure setpoint
  is between 0 and 40 and moves by at most 5" is a sentence the configuration
  can hold. See below.
- **The schedule**, so switching can be limited to the day shift.
- **The rate**, with `command_rate_limit` separate from the frame rate: a
  control channel carrying a thousand measurements a second and two commands an
  hour needs two different bounds.

`STOPDT_act` is worth a note. It is not a command and changes nothing in the
field, so it is easy to overlook — and a client that sends it has stopped data
transfer, which blinds a control room without refusing a single command. An
empty `allow_controls` allows all four control functions, so excluding it means
**naming the ones you want**: `STARTDT_act` and `TESTFR_act` and their
confirmations, and not that one.

### Redundancy groups, and the state that has to survive a failover

A group is declared rather than inferred, because declaring it buys two things
that pull in opposite directions.

**A control.** Without a group, a second connection from the control centre's
own network is just another client, and an injected command on it is decided
exactly like one on the first. With a group, only the connection holding data
transfer may send anything: an I frame from a standby path is refused before it
reaches the station, and taking data transfer from a live path is a failover,
logged as `iec104_failover` and refusable outright with `takeover: refuse`.

**A concession.** Select-before-operate is enforced by remembering a selection,
and a selection belongs to the connection that made it — so a failover between
the select and the execute turns a legitimate two-step command into a refusal.
A control room that meets that during an outage turns `require_select` off, and
then the protocol's one safety property is gone for good. `carry_selects`
(default on inside a group) keeps the selection across the group instead.

What that trusts is the group's `clients` list: any address in it can consume a
selection another connection made. What bounds it is the control above — the
selection can only be consumed by whichever connection currently holds data
transfer, so an intruder inside those networks has to win a `STARTDT` first, and
that is a logged failover rather than a quiet execute. Validation warns when a
group carries selections across a client list wide enough that the list is not
really an assertion about two or three paths.

The setpoint memory needs none of this: it is keyed on the point rather than on
the connection, and was already per listener, because the process does not reset
when a control centre reconnects — a delta bound that did would be a bound any
client could clear by dropping its association.

**Three refusals, not one.** `unselected` is a bare execute that was never
selected. `select_expired` is an operator who selected a point and came back to
it too late. `select_other_connection` is a two-step command that was done
properly and a failover in the middle dropped — which is the diagnosis nobody
can make from outside the relay, and the one that tells a control room its
failover is losing selects rather than that somebody is injecting commands.

### The value bound on a setpoint

A rule says a control centre may command point 4711. It says nothing about what
4711 may be set *to*, and on this protocol nothing else does either: a scaled
setpoint (`C_SE_NB_1`) carries any integer from -32768 to 32767, a short float
(`C_SE_NC_1`) most of the real line, and the RTU will write whatever arrives. A
governor setpoint, a tap-changer position or a reactive-power reference driven
to the end of its encoding is a fault that looks, frame by frame, exactly like
ordinary operation.

`setpoints` is where the process is bounded:

```yaml
setpoints:
  - name: pressure
    points: ["4711"]
    types: [C_SE_NB_1]     # a scaled value, in the point's own unit
    min: 0
    max: 40
    max_delta: 5           # it may be nudged, not jumped
    on_unknown: allow      # what to do before the relay has seen the point
```

The two halves are different in kind, and the difference is the honest part.
`min` and `max` are a statement about a value: they need nothing, they are
checked first, and they hold for every setpoint command including a
*selection* — the station is never asked to hold a value it may not be given.
`max_delta` is a statement about a change, so it needs to know where the point
is now, and what that means here is **the last value this relay saw**: a
setpoint it forwarded, or a station's positive confirmation of one. A value
changed by another control centre, by a local panel or by the process itself
was never on this path. So `on_unknown` says what happens when there is no
previous value — `allow` carries the command with the range still in force,
`refuse` holds it — and `iec104_setpoint_unknown` counts how often that
happened, because a policy running on less than it asks for should be visible
rather than silently permissive. A station's *negative* confirmation makes the
relay forget the point: the command did not take effect, so a delta measured
from it would be measured from a value the equipment refused.

**A normalised setpoint is a fraction, not an engineering value.** `C_SE_NA_1`
carries the standard's *normalised* value: a signed 16-bit number over 2^15, so
-1 to very nearly +1, and the full scale it is a fraction of lives in the
device where this relay cannot see it. A bound on a normalised point is
therefore a bound on the fraction (`max: 0.8`), and `max: 40` on one is a bound
nothing can exceed. The load warns when a bound named only for normalised types
is written outside that range; it cannot warn when the same bound also covers a
scaled type, because there the numbers are right. This is the reason the
earlier versions of this listener had no value policy at all, and it is a
warning rather than a refusal because one bound written in the wrong units is
better found at load than at a breaker.

### What the information element says

The header of an ASDU says what kind of thing is being reported and about which
addresses. The element says the thing itself, and three of the questions an
operator most wants asked live there.

**Is this value real?** Every monitored type but `M_ME_ND_1` carries a quality
descriptor. `SB`, substituted, means a person typed the value in rather than an
instrument measuring it; `IV`, invalid, means the device says not to trust it.
`quality` names the bits worth a security event -- `substituted` by default,
because it is the one no HMI in the field shows -- and, if an estate insists, the
bits that refuse the frame. The default is alert and carry, because a relay that
refused telemetry would blind a control room, and an alert here does not reach the
ban ladder: a substation with a hand-entered reading is not an attacker.

**When did this happen?** A time-tagged command carries a CP56Time2a, and a
command replayed an hour later carries the hour-old timestamp with it. **Nothing
in IEC 60870-5-104 makes a station compare that against its clock**, so a
recorded breaker command, sent again, opens the breaker again. `timestamps` is
that comparison: `max_command_age`, `max_command_future`, `require_on_commands`
and `deny_invalid`. Those refusals are hard -- a command forwarded so that its age
could be written down is a moved actuator. The comparison is against this relay's
clock, so a substation whose clock is wrong trips it, which is a finding rather
than a false positive and is why the `ntp` kind exists.

**What is the value?** `measurements` bounds what a station may claim to have
measured on a point, which is the arithmetic of `setpoints` pointed the other way.
A pressure of 900 bar on a 40 bar transmitter is either a broken instrument or a
forged frame, and either way an operator should be told rather than have it sit on
a trend. `action: alert` is the default and `action: deny` is available.

Every object of an ASDU is walked, not only the first: a report carrying forty
measurements carries forty chances for one of them to be the substituted one, and
a check that read only the first would be one a station could evade by ordering
its report. See [docs/CONFIG.md](../CONFIG.md#serverlistenersiec104timestamps).

### IEC 62351-5, and the limit of what a relay can say about it

IEC 60870-5-7 -- the application layer IEC 62351-5 specifies -- adds the
authentication the protocol itself has none of: the controlled station challenges
a critical command with `S_CH_NA_1`, the controlling station answers with
`S_RP_NA_1` carrying an HMAC over it, and only then is the command acted on.
Aggressive mode carries the authentication with the command instead.

**This relay recognises the exchange and carries it; it does not verify it.**
Verifying means holding the update keys, and a relay holding them would be a
second place to take them from -- one that failed closed on a key it had got
wrong would stop a control centre operating a grid. No HMAC is computed, no key
is stored, and nothing is claimed about whether an authentication was *valid*.

Three things are claimed. The exchange **is not refused**: before the thirteen
`S_*` types were named, a listener saw type 81 as an unknown type and refused it,
which made the standard's own authentication unusable through the relay. Whether
it happened **is visible**, in `iec104_authentications`, counted whether or not
the listener requires it -- which is how an estate decides whether to require it.
And it **can be required**: `authentication: {require: true}` refuses a command on
an association that has shown no reply or aggressive-mode request inside a window.
A relay cannot tell a good HMAC from a bad one; it can tell an exchange from no
exchange, and on this protocol that is the difference between a station running
the standard's authentication and one with it switched off.

The state is per association, because crediting one connection's exchange to
another would let a client that can open a socket ride on a legitimate control
centre's authentication. See
[docs/CONFIG.md](../CONFIG.md#serverlistenersiec104authentication).

### The relay is an end

This protocol numbers every I-format frame in each direction, contiguously,
and a conforming implementation closes the connection on a gap rather than
trying to recover — the reference implementation does it on the controlling
side and again on the controlled side.

That makes pure forwarding impossible for a relay that refuses anything. The
moment one frame is refused, the stream written on is short a number: the end
reading it sees a gap where the refused frame's number should be and drops
the association, taking the substation's telemetry away with the refused
command. The same arithmetic runs the other way, because the refused frame
consumed one of the sender's numbers and never reached the station. Twelve
refusals would also fill the sender's window with frames nothing will ever
acknowledge.

So the relay is an end of the association at the APCI layer:

- It numbers the frames it writes, from its own count per direction.
- It acknowledges what it reads, at `w` and on a timer for a link too quiet
  to carry an acknowledgement on a frame going the other way. The standard's
  t1 is 15 seconds and an end that is not acknowledged inside it closes.
- It terminates the supervisory frames. An acknowledgement is about the
  stream this relay wrote, so passing one on would be telling the station
  something the control centre never said.

The application layer is untouched: the ASDU that arrives is the ASDU that
leaves, byte for byte, because re-encoding it is how a relay and a station
come to disagree about what was said. Only the six control octets are the
relay's own.

### Learning what the traffic is

`learn` records what crosses this listener and writes a proposed policy, for the
reason the modbus relay has one: nobody knows what a substation's traffic
actually is. The drawings say which points exist and which of them a control
centre is supposed to command; the traffic says what the integrator left behind.
A policy written from the drawings refuses half of it on the first shift, which
is how a security control gets turned off and stays off.

A learning run is observe-only unless `enforce` says otherwise, which is the
point: a run that refused half the traffic would have changed the thing it was
measuring. A subject is one client, one direction, one common address and one
type identification — the direction because the same type means different things
each way, and a report that folded them together would propose a rule allowing a
station to command its own control centre.

Three things in the report are worth reading before the proposal. `causes` is
what the subject actually used, which is the part of an IEC 104 rule most often
written too loosely. `denied_by_policy` counts what the current policy refused,
or would have refused — a subject the policy and the traffic disagree about.
`refused_by_equipment` counts the negative confirmations the station sent for
that command: the equipment will not do it, so it belongs out of the policy, and
the proposal leaves it out.

The measurements travelling up are deliberately not in the report; a setpoint's
span is, because that is the bound `setpoints` is written from. See
[docs/CONFIG.md](../CONFIG.md#serverlistenersiec104learn).

### A station that is not there

`deception` answers as a substation the estate does not have. Two shapes:
`mode: answer` confirms an activation this listener was going to refuse, on a
listener that fronts a real station; `mode: decoy` is the whole listener, a
fabricated station with no upstream at all.

The rule that bounds it is a test rather than an intention: **a frame that
was going to reach a station is never answered by the fabrication.**
Deception replaces the negative confirmation a refusal would have sent, and
nothing else — so the worst case of a false positive is a control centre told
"no" in a way that looks like "yes", never an operator reading a fabricated
measurement off a real point. `mode: answer` will not load without
`clients`, and a decoy will not load with an `upstream`.

A decoy answers the association the way the standard describes it: nothing
before `STARTDT_act`, a confirmation, then `M_EI_NA_1` for the end of
initialisation; a general interrogation answered ACTCON, the points at cause
20, then ACTTERM; a common address it is not answered negatively with cause
47. The values are derived from a seed, the information object address and
which period of the clock it is, so they are stable while a centre reads
them and have moved when it comes back. `tripwire` names the addresses
nothing legitimate reads: those are answered too, and raised as
`iec104_tripwire`, which is the event an operator acts on. See
[docs/DECEPTION.md](../DECEPTION.md#a-substation-that-is-not-there).

### The imported lists, and the estate's authorisation policy

IEC 104 names nobody: a controlling station is an address and a common address. So
two questions are asked about the client itself, after this listener's own
`allow_clients` and before the station is dialled:

- **the imported address lists** (`threat_intel`), about the client's address. A
  list whose action is `block` refuses; one that asks for a `challenge` is
  recorded like a log list, because there is no request here to serve a challenge
  into and turning it into a block would be a policy the operator did not write.
- **the `authorization` section**, on the client address, the listener, the kind,
  the upstream pool and the hour. A rule naming `users` matches nobody on this
  kind, so a rule here is written with `networks`, `targets` and `schedule`.

Which type identifications and which information objects that station may then
touch stays with this listener's own policy above -- and so does the
select-before-execute rule, which is the thing only it can enforce.

The lists are asked first: a list is an import about an address and says nothing
about this estate's intentions, so a refusal naming the feed sends an operator to
the feed rather than to a rule they would not find.

A refusal is the reason `threat_intel` or `authorization` on this listener's usual
deny event, so the counters, the security log and the ban list see it as they see
any other refusal. Either shadow switch -- `policy: {mode: shadow}` on the
listener, or `shadow: true` on the section -- records what it would have refused
and carries the traffic.

## Behavioural detection

`anomaly` is the other half of the policy, and it needs nothing written down.
The rules answer *is this permitted*; the models answer *is this what this
control centre has been doing*. They are `internal/anomaly`, the same six models
every OT kind runs, and [docs/CONFIG.md](../CONFIG.md) documents the block once.
The translation on this protocol is unusually direct:

| The models' term | On IEC 104 | Used by |
|------------------|------------|---------|
| symbol | the type identification: `C_SC_NA_1`, `M_ME_NC_1` | novelty, sequence |
| device | the common address, which is the substation | talkers |
| point | common address and information object address, `station 1 4321` | novelty about writes, telemetry, correlations |
| value | a setpoint a centre commanded, and every measured value a station reported | telemetry, correlations |

A write, to the models, is a command with a cause of transmission that is
commanding: the same type identification carries a command and its confirmation,
and only the first is something the centre did.

**The rhythm is worth more here than almost anywhere.** A control centre's
general interrogation cycle is configuration, not a per-request choice, so a
poller that has asked every thirty seconds for a year and now asks ten times a
second is a different program whatever it is asking for. That is
`anomaly_cycle_changed`.

**Telemetry runs the value models and nothing else, and is never refused.** A
station's answer is not something the controlling station did: counting it as a
request would teach the cycle model a rhythm that is the sum of the commands and
the telemetry. And by the time an answer has arrived there is nothing left to
refuse -- refusing telemetry would take the control room's view away over a
detection about that view. A measured value that has stopped moving, or a run of
readings that repeats exactly, is `anomaly_telemetry_frozen` or
`anomaly_telemetry_replayed`.

## Engineering activity

On IEC 60870-5-104 the type identification says which commands are a control
room's work and which are a substation's. The `engineering` block —
[documented once in docs/CONFIG.md](../CONFIG.md#engineering), the same on every
OT kind — reads the second group as its own class of event, and can hold them to
an approved grant out of the [access ledger](../CONFIG.md#access).

| Type | Class | Why |
|------|-------|-----|
| `C_RP_NA_1` | `restart` | Reset process |
| `C_CS_NA_1` | `configuration` | The clock every event in the substation is stamped with |
| `P_ME_NA_1` … `P_AC_NA_1` | `configuration` | Parameters of measured values, and their activation |
| `F_FR_NA_1` … `F_SC_NB_1` | `file_transfer` | SCL, disturbance records, firmware |

**A single or double command is not engineering.** That is a breaker being
operated, and it is what the rules and the select-before-operate machinery are
for.

**The parameters are the interesting case.** A parameter of a measured value is
the deadband and the scaling a control centre sees its own telemetry through, so
changing one changes what the operators are looking at without touching a single
measurement. There is no command in the trace and the screens are wrong.

Only an ASDU whose cause of transmission is a *command* is classified: the
station's own answers travelling up carry the same type identifications, and
counting a confirmation as an engineering operation would put the substation in
the work-order record beside the engineer.

## What it does not do

- **It does not decide which path of a redundancy group should be active.**
  That is the controlling station's own decision and the relay follows it: a
  group's `STARTDT` moves data transfer, and the relay records, logs and
  optionally refuses the move. It does not promote a standby path itself, and
  it does not tell a control centre that its active path has failed.
- **A redundancy group is an assertion, not a proof.** The `clients` list is
  what says those connections are one controlling station, and nothing on this
  protocol can verify it: IEC 104 names nobody, so an address is what an
  attacker on the same segment chooses. Where the equipment supports
  IEC 62351-3, the listener's TLS with mutual authentication is what turns the
  assertion into something checked; without it, a narrow client list and
  `takeover: refuse` are what is left.
- **It does not invent select-before-operate at the device.** `require_select`
  makes the relay refuse an unselected execute; it cannot make a device that
  accepts direct execute stop accepting one from something that reaches it
  another way.
- **It does not translate between -101 and -104.** A serial link is a different
  physical world; this listener is the TCP protocol only.
- **It does not hide a numbering fault.** `check_sequence` verifies the send and
  receive numbers and refuses a frame whose numbering cannot be right, with
  `iec104_sequence_gaps` counted and the refusal logged. What it does renumber
  is its own output, because it has to (see *The relay is an end* above); a
  gap in what *arrived* is reported and never patched over.
- **It does not know a normalised point's full scale.** `setpoints` bounds a
  value, and for a scaled or short-float setpoint the number is the engineering
  value. For a *normalised* one it is a fraction of a full scale configured in
  the device, which no relay can read off the wire — so a bound on one of those
  is a bound on the fraction, and the load can only warn when it looks as
  though it was written in engineering units.
- **It does not know what a point holds unless it saw it.** `max_delta` is
  measured from the last value this relay forwarded or saw confirmed. Another
  control centre, a local panel or the process itself changes a point without
  passing through here, and `on_unknown` is the knob that says what to do about
  that rather than a claim that it cannot happen.
- **It does not terminate TLS for the plain port.** IEC 62351-3 is its own
  listener on its own address, because a protocol whose security starts at the
  first octet should not share a port with one that has none.
