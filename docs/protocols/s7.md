# S7comm — Siemens PLCs

`kind: s7`, served by **xot**, TCP port **102**.

The protocol an engineering station speaks to a Siemens S7-300, S7-400,
S7-1200 or S7-1500. It is not a public standard: Siemens has never published
it, and every implementation outside Siemens — including this one — is built
from the protocol's documented *transport* layers plus a body of work by other
people reading the wire.

## On the wire

Three protocols stacked, and each has to be read before the next one means
anything.

| Layer | What it is | What it carries |
|-------|-----------|-----------------|
| **TPKT** | RFC 1006, "ISO transport services on top of the TCP" | A version octet, a reserved octet and a 16-bit length. That length is the sender's choice, so it is checked against a bound before anything is allocated |
| **COTP** | ISO 8073 / X.224 class 0 | The transport PDU type, and — in a *connection request* — the calling and called TSAPs. The called TSAP is where the address of the CPU is |
| **S7comm** | Siemens', undocumented | A protocol identifier of `0x32`, a message type (job, ack, ack-data, userdata), a PDU reference, and a parameter and data block whose lengths are declared in the header |

The **called TSAP** is the field that matters most, because it is the only
place the protocol says which controller a client wants. Two octets: a
*connection resource* — `0x01` for the programming device connection an
engineering station opens, `0x02` for an operator panel, `0x03` for what one
PLC opens to another — and then a rack (three bits) and a slot (five bits).
It arrives in the connection request, before any S7 message exists at all.

Inside S7comm the operation is spread across **two layers**, which is the
single most important thing about writing a policy for it:

- A **function code** covers reading and writing memory (`0x04`, `0x05`), the
  negotiation (`0xF0`), the block services (`0x1A`–`0x1F`) and the control
  and stop services (`0x28`, `0x29`).
- A **user-data group and subfunction** covers everything else: the system
  status lists, the diagnostic buffer, the block list, the cyclic
  subscriptions, the clock, the password functions and the debugger.

A read or a write names memory through *item specifications*: an area (`0x84`
is a data block, `0x81` and `0x82` are the input and output process images,
`0x83` the flags Siemens calls merkers), a block number, a transport size, a
count — and a **bit** address, which is the byte address multiplied by eight.

## What the protocol gives you

Nothing. This is the listener for the protocol with the least security of any
in this project, and the sentence is not rhetorical:

- **No transport security.** There is no TLS, no STARTTLS, no in-protocol
  upgrade and no extension that adds one. Everything is in the clear, and
  anything on the path can rewrite it.
- **No authentication worth the name.** There is an optional password, and
  what it protects depends on the CPU family: on some it covers a handful of
  functions, on others nothing at all. An S7-300 with no password set accepts
  a **stop** from anybody who can open a socket to TCP 102.
- **No session, no identity, no authorisation.** A request says what to do and
  where; the controller does it.

So an engineering station on the same segment can read and write every byte of
memory in every controller on that segment, and stop any of them.

The equipment cannot be fixed. A controller in a production line is replaced
on a capital cycle, not a release cycle, and its firmware is qualified against
the physical process it runs — a plant does not take a patch from a vendor
without a requalification that costs a shutdown. So the boundary has to be
somewhere else.

## What this listener decides

**The controller, before the PLC is dialled.** The rack, the slot and the
connection resource come out of the COTP connection request, so a client that
may not reach that CPU is answered with a COTP disconnect request — what a
controller with no free connection resources sends — and the PLC is never
contacted. That ordering is the point rather than an optimisation: an S7-300
has *sixteen* connection resources altogether, and a client that may not reach
it should not take one of them.

`resources` is the cheapest useful line in the section. A listener that admits
only `op` has refused every engineering station without naming a single
function.

**The operation, in one vocabulary spanning both layers.** Nineteen words
cover the function codes and the user-data groups together, because a policy
written against either alone would have nothing to say about half the
protocol. The default allows what an HMI, a historian and an inventory do —
reading memory, the status lists, the block list, a cyclic subscription, the
clock and the diagnostic machinery — and nothing that changes anything.

Two consequences are worth naming:

- `read_only` means **every** operation that changes the controller, not just
  a write: the downloads, the control service, the stop, the mode transitions,
  the clock setting, the password functions and the debugger. No rule can
  override it, because a read-only listener one rule could write through is
  not a read-only listener.
- An **upload is off by default** although it changes nothing, because reading
  a block out of a PLC is how a plant's control logic leaves the site.

**The memory.** The area, the data block and the byte range, checked against
the **whole span** a request covers rather than its first byte: a read of
bytes 0 to 200 against a range of 0 to 99 is a read of bytes the policy does
not name, and it is refused rather than clipped, because clipping it would be
the relay deciding which half the operator meant. The ranges are written in
bytes and the protocol carries bits, so the relay divides by eight rather than
making anybody else do it.

**The bounds.** Items per request, octets per request, the negotiated PDU
length, the frame size, requests per second, and concurrent sessions per
client — the last because of those sixteen connection resources.

A refused request is **answered and the session carries on**: an
acknowledgement carrying error class `0x87`, *access fault*, which is what a
password-protected CPU answers a client that has not supplied a password. The
client's own library reports a refusal rather than sitting in a timeout, and
the poll loop a plant runs on is not turned into an outage by one refused
request. A refused user-data request is answered in *its* layer, with the same
group and subfunction and the error code for a function the CPU does not
offer, because that is where a client that asked to set the clock looks.

An access fault arriving *from the controller* is logged as
`s7_plc_refused`. That is the CPU refusing something this listener allowed,
which on this protocol almost always means the controller is
password-protected and the client has not supplied one — the case where the
two policies disagree, and an operator has to decide which one to change.

### S7comm-plus, and the limit of what a relay can see

Everything above is *classic* S7comm — what an S7-300 or S7-400 speaks, and what
a Siemens controller bought before about 2012 speaks. TIA Portal talking to an
S7-1200 or S7-1500 speaks **S7comm-plus**: the same TPKT and COTP stack, a
protocol identifier of `0x72` instead of `0x32`, and a different protocol above.

A relay that read only `0x32` was not a relay in front of those controllers at
all. It ended the connection on the first S7comm-plus PDU — no answer in the
protocol, nothing in the counters an operator would read as a policy — so the
newest half of a Siemens estate could not be put behind it, and the failure
looked like a network fault rather than a decision.

`s7comm_plus` decides what happens to it, with three modes: `refuse` (the
default, and what an `s7` listener written before this existed meant — but now
named and counted), `policy`, and `passthrough`.

**What is left to police, and what is not.** Much less than in classic S7comm,
and the difference is not the relay's to fix. On the controllers that speak
S7comm-plus the session is integrity-protected and the object and variable
addressing is encrypted under a key the two ends derive. A relay in the middle
sees the outer framing and nothing under it. So the policy is written about the
**function code** — whether this is a read, a write, a method call or a program
change — and `areas`, `dbs` and `addresses` simply do not apply to it. A section
that claimed to bound data blocks on this protocol would be claiming to read
something no relay can see, and that claim would be worse than the gap.

**The names come from the wire, and the design says so.** Siemens publishes no
specification for either protocol; the function names here are the ones public
reverse engineering agrees on. That is a weaker footing than an RFC, so one
property carries the weight: a function code this relay cannot name is the
`unknown` class, and `default_action` decides it — `deny` unless an operator
says otherwise. An incomplete table costs a refusal, never a silent pass, and
`unknown` is nameable in a list so that the decision about it is visible rather
than inherited. The `read_only` switch covers it too: on a read-only listener
the one function that must not be carried is the one nobody can name.

**And one shape of PDU cannot be inspected at all.** From firmware 1.5 a
variable-length integrity block sits in front of the opcode, so the function
code is not at a findable offset. Those PDUs are the `opaque` class — named, so
an operator can allow them with their eyes open, and refused by default. A
current S7-1500 sends them constantly, so allowing `opaque` is what makes such a
controller work, and it is close to `passthrough` for that traffic; the
reference says so rather than burying it in a class list.

**There is no way to say no.** Classic S7comm has a refusal — an
acknowledgement carrying an access fault, what a password-protected CPU answers
— so a refused classic request is answered and the poll loop carries on.
S7comm-plus has no response this relay can build, and inventing one would put
octets on the wire no controller would send. So `deny_response: error` degrades
to `drop` for it: the request is swallowed and the engineering station reads a
timeout for that one request. `deny_response: close` ends the session instead.
The load warns about this rather than leaving it to be found in the field.

### Learning what the traffic is

`learn` records what crosses this listener and writes a proposed policy, for the
reason the modbus and IEC 104 relays have one, only more so: on this protocol
there is nowhere else to find out. The CPU keeps no access log, and nobody can
enumerate the blocks a program touches by reading the program. The drawings say
which blocks a controller has; the traffic says which of them the integrator's
HMI reads every second, which one the historian polls, and that the commissioning
laptop has been reading DB1 since 2014.

A learning run is observe-only unless `enforce` says otherwise, which is the
point: a run that refused half the traffic would have changed the thing it was
measuring. A subject is one client, one operation, one area and one data block —
the grain an S7 rule is written at — and within a subject the byte ranges are
merged as they grow, with what was written kept apart from what was read.

Three things in the report are worth reading before the proposal.
`denied_by_policy` counts what the current policy refused, or would have refused.
`access_faults` counts what the **controller itself** refused, which on this
protocol almost always means a password-protected CPU: the equipment already says
no, so the proposal leaves a subject it always refuses out. A fault is charged to
the operation it answers and to nothing else, so a CPU that refuses writes and
answers reads does not cost the HMI its read. And `operation: unknown` is a
request this relay could not name — the raw function code is listed beside it and
no rule is proposed for it, because a proposal naming an operation outside the
vocabulary would not load.

No value is recorded, and neither is S7comm-plus: its policy is about opcodes
rather than areas and blocks, and one report cannot propose rules in both
vocabularies. See [docs/CONFIG.md](../CONFIG.md#learning-what-the-traffic-is).

### A controller that is not there

`deception` answers as a CPU the estate does not have: `mode: decoy` is a whole
listener with no upstream, and `mode: answer` fabricates, on a listener that
fronts a real controller, the answers to requests it was going to refuse.

The reason it earns a place on this protocol in particular is the system status
list. It is the first thing every scanner asks for and the thing no policy here
can usefully narrow, because the estate's own asset tools read the same list: a
refusal says "there is a relay in front of something", and an answer says which
controller. A fabrication says neither.

What bounds it is a test rather than an intention: **a request that was going to
reach the controller is never answered from here**, and beyond that only a read,
a write and the identification lists are fabricated at all. Every other refused
function keeps the access fault a protected CPU sends, because a fabrication
that acknowledged a stop would be telling a client a machine had stopped.
`mode: answer` will not load without `clients`, and a decoy will not load with
an `upstream`.

The identity is the operator's to choose, and the profiles are deliberately
ordinary. Both are classic families — a decoy answering classic S7comm while
claiming to be an S7-1500 is a contradiction a scanner sees in one exchange, so
this one answers an S7comm-plus request the way a 300 does: with a COTP
disconnect. See
[docs/DECEPTION.md](../DECEPTION.md#a-controller-that-is-not-there).

### The imported lists, and the estate's authorisation policy

S7comm names nobody: a client is an address and a rack and slot. So two questions
are asked about the client itself, after this listener's own `allow_clients` and
before the PLC is dialled:

- **the imported address lists** (`threat_intel`), about the client's address. A
  list whose action is `block` refuses; one that asks for a `challenge` is
  recorded like a log list, because there is no request here to serve a challenge
  into and turning it into a block would be a policy the operator did not write.
- **the `authorization` section**, on the client address, the listener, the kind,
  the upstream pool and the hour. A rule naming `users` matches nobody on this
  kind, so a rule here is written with `networks`, `targets` and `schedule`.

Before the PLC is dialled matters more here than on most kinds: an S7-300 has
sixteen connection resources altogether, so a client that may not reach the CPU
should not take one of them while being refused. Which functions and which data
blocks it may then touch stays with this listener's own policy above.

The lists are asked first: a list is an import about an address and says nothing
about this estate's intentions, so a refusal naming the feed sends an operator to
the feed rather than to a rule they would not find.

A refusal is the reason `threat_intel` or `authorization` on this listener's usual
deny event, so the counters, the security log and the ban list see it as they see
any other refusal. Either shadow switch -- `policy: {mode: shadow}` on the
listener, or `shadow: true` on the section -- records what it would have refused
and carries the traffic.

## Behavioural detection

`anomaly` is the other half of the policy, and it needs nothing written down.
The rules answer *is this permitted*; the models answer *is this what this
engineering station has been doing*. They are `internal/anomaly`, the same models
every OT kind runs, and [docs/CONFIG.md](../CONFIG.md) documents the block once.
The translation on this protocol:

| The models' term | On S7comm | Used by |
|------------------|-----------|---------|
| symbol | the operation: `read variable`, `download block`, `userdata cpu functions` | novelty, sequence |
| device | the rack and slot the session addressed | talkers |
| block | the area, block and byte range a write touched, `DB 12 byte 100-119` | novelty about writes |
| point | area, block and byte, `DB 12 byte 100` | — |
| value | nothing | — |

**The value models have nothing to work with here, and the reference says so
rather than pretending.** An S7 item is octets whose meaning lives in the
engineering project, not on the wire: this relay cannot turn a controller's
answer into a number without guessing at a data type, and a telemetry model fed
the first two octets of something would report about a value nobody has. So
`telemetry` and `correlations` are inert on an `s7` listener, and the other four
models carry the kind.

**The order model earns its place on this protocol.** An engineering tool reads a
block, writes it and reads it back, in that order, every time; an HMI never
writes twice in a row. `anomaly_sequence_unseen` is a legitimate-looking
operation in a place this station has never used it, which is what a tool that is
not this station's tool looks like.

**S7comm-plus has no refusal to write** (see *What it does not do*), so a
behavioural finding on a plus PDU alerts and the request goes on. A silent drop
for a signal derived from novelty would be the worst of both.

## Engineering activity

S7comm is the protocol the engineering class is easiest to argue for: the
operations an engineering station uses are *named on the wire*, and they are the
operations a plant is compromised through. The `engineering` block —
[documented once in docs/CONFIG.md](../CONFIG.md#engineering), the same on every
OT kind — reads them as their own class of event, and can hold them to an
approved work order out of the [access ledger](../CONFIG.md#access).

| On S7comm | Class | Why |
|-----------|-------|-----|
| `download` | `program_download` | Control logic into the CPU |
| `upload` | `program_upload` | Control logic out of it — how a plant's process knowledge leaves the site |
| `stop`, `mode` | `mode_change` | Run, program and stop |
| `programmer` | `mode_change` | A variable forced, a breakpoint set: the CPU is no longer only running its program |
| `control` | `restart` | Warm restart, block insert |
| `time_write` | `configuration` | The clock every batch record and every sequence is timed against |

**A read is not engineering, and neither is a write to a data block.** An HMI
writes setpoints all day, and a class that included those would be a class
nobody could read. The line is "this changes what the machine *is*, not what it
is doing" — which is why `write variable` is the rules' and the value bounds'
business and `download block` is this section's.

The operation is reported whatever the rules said about it: a security event
with `action: engineering`, the class, `describe()`'s own words for the request,
and the counter. With `engineering: {require_grant: true}` a download with no
open approved grant is refused with `engineering_no_grant` and answered as an
S7 error, and the CPU never sees the request. Without one, a download outside
every approved window is still alerted as `engineering_ungranted`.

**S7comm-plus is a gap here and the reference says so.** The addressing is
encrypted, so on an S7-1200 or S7-1500 this relay sees the function code and
not what it touched. A plus download is classified from the function alone:
the class is right, the detail is thinner, and the work order is what makes up
the difference.

## What it does not do

- **No TLS section.** The protocol has none to negotiate, and a certificate
  here would promise something it cannot do. Traffic that has to cross
  anything the plant does not own belongs in a tunnel whose security is real,
  with this listener at the far end of it.
- **It does not rewrite the negotiation.** A PDU length above
  `max_pdu_length` is refused, not lowered: rewriting a negotiation makes the
  relay a party to it, and a session that agreed a length and then had a
  transfer refused half way through is a harder fault to find than one that
  failed at the start.
- **It does not log values.** A write's payload is a process value — a
  pressure, a temperature, a recipe parameter. The *address* is logged,
  because an address is what a policy is written about, and a refusal nobody
  can attribute to a byte range is a refusal nobody can act on.
- **It does not guess.** A function code nobody has documented, a user-data
  group outside the nine, an item list that does not lay out, an item written
  in the symbolic syntax rather than S7ANY: each is refused rather than
  forwarded, because an operation with no name is an operation with no policy.
- **It does not re-encode.** The only frames this listener writes are its own
  refusals. A proxy that re-rendered a peer's frame would be a second
  implementation of the encoder, and the disagreements between the two are
  what an attacker is looking for.
- **It does not read inside S7comm-plus.** The session is
  integrity-protected and the addressing encrypted, so what a request on an
  S7-1200 or S7-1500 *touches* is not visible to anything in the path. The
  function code is, and that is what the policy is written about. Nothing here
  verifies the integrity protection either: a relay cannot, without the session
  key the two ends derive between themselves.
- **It is not a firewall for the segment.** A client that can reach TCP 102 on
  the controller directly is not covered by anything here. The listener is
  worth what the network path makes it worth.

## Standards

| Document | What it covers |
|----------|----------------|
| RFC 1006 | ISO transport services on top of the TCP — the TPKT framing |
| RFC 2126 | ISO transport over TCP, the IPv6 revision |
| ITU-T X.224 / ISO 8073 | The connection-oriented transport protocol; class 0 is what runs here, and where the TSAP fields are defined |
| ITU-T X.214 / ISO 8072 | The transport service definition the TSAP addressing comes from |
| IEC 62443 | The industrial security framework a plant's zone and conduit model is usually written against; this listener is a conduit in those terms |

S7comm itself has no specification. What this listener reads is the intersection
of the transport standards above and the message structure that is stable
across the CPU families in the field.
